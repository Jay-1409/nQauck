Proposal · no code changes

Make SMTP outages survivable.

Recommended: use durable Kafka retry topics for temporary SMTP failures, then send exhausted or permanently invalid messages to a dead-letter topic. This protects the consumer from retrying one message forever and preserves every failed request for review or replay.

What happens today

The Kafka worker catches every processing exception, seeks back to the same record, waits one second, and does not commit its offset. An offline SMTP server therefore retries forever and blocks that Kafka partition. There is no durable retry state, attempt limit, or dead-letter record.

Target message path

Kafka has no RabbitMQ-style broker TTL/DLX. The worker will own the retry schedule: it writes the failed record with retry metadata, commits the original offset, and only delivers retry records when their due time arrives.

Implementation plan

01 · Classify
Separate retryable from permanent failures.
  • Retry SMTP connection, read, and write timeouts; connection refused; and transient 4xx SMTP responses.
  • Dead-letter malformed payloads, missing required email fields, invalid recipient addresses, and permanent SMTP/auth failures.
02 · Retry durably
Move—not seek—the failed record.
  • Publish the original message to email.retry with attempt number, next-at time, original topic/partition/offset, and concise failure metadata.
  • Commit the source offset only after the retry publish succeeds, preventing duplicate loss.
03 · Bound the outage
Use a short, predictable backoff policy.
  • Recommended initial schedule: 1 min → 5 min → 15 min → 1 hr → 4 hr.
  • After the fifth failed delivery, publish to email.dlt and commit the retry offset.
04 · Make failures operable
DLT is a workflow, not a bin.
  • Log and count retry/DLT transitions without logging message bodies or credentials.
  • Add a small operator action later: inspect DLT metadata and replay selected messages after SMTP recovery.

Safety and scope

  • Preserve the existing Kafka key when republishing, so related messages maintain partition ordering.
  • Do not silently drop any record; each terminal failure must be in email.dlt.
  • Keep SMTP credentials and email HTML out of logs and DLT failure text.
  • Initial implementation covers Kafka only. RabbitMQ needs its own DLX/TTL policy later; its native dead-letter exchange makes that a separate, smaller change.
